# System Design and Data Integrity

## Data model

### `accounts`

| Column | Type | Rule |
|---|---|---|
| `id` | UUID | Primary key, generated by server |
| `name` | VARCHAR(120) | Not null; non-empty after trimming at API boundary |
| `balance_minor` | BIGINT | Not null, default 0, check >= 0 |
| `created_at` | TIMESTAMPTZ | Not null, generated by server |

### `transactions`

| Column | Type | Rule |
|---|---|---|
| `id` | UUID | Primary key, generated by server |
| `account_id` | UUID | Not null, FK to accounts, indexed |
| `type` | ENUM/TEXT | `credit` or `debit`, database check constraint |
| `amount_minor` | BIGINT | Not null, check > 0 |
| `description` | VARCHAR(500) | Not null |
| `reference_id` | VARCHAR(128) | Not null |
| `created_at` | TIMESTAMPTZ | Not null, generated by server |
| `transfer_id` | UUID nullable | Optional grouping for paired transfer entries |

Constraints and indexes:

- Unique `(account_id, reference_id)`.
- Index `(account_id, created_at DESC, id DESC)` for history.
- Check `amount_minor > 0` and valid transaction type.
- Foreign key `account_id -> accounts.id`.
- No update/delete endpoints. Restrict app DB role to INSERT/SELECT on transactions if practical; balance changes only on account rows.

## Money representation

Use integer paise in storage and exact decimal strings over JSON. Parse decimal input without converting through JavaScript `number`: split whole/fractional parts, normalize to two digits, convert to `bigint`, check bounds, then persist. Serialize minor units as `major.minor` with two digits. Never sum with floating point.

## Atomic credit/debit algorithm

Execute all steps below on one PostgreSQL connection within one transaction:

1. Lock the account row using `SELECT ... FOR UPDATE`.
2. If no account row exists, return `ACCOUNT_NOT_FOUND`.
3. Look up `(account_id, reference_id)`; if present, return the existing transaction as a duplicate without changing state.
4. For debit, compare `balance_minor >= amount_minor`; otherwise raise `INSUFFICIENT_FUNDS` and roll back.
5. Insert one immutable transaction row.
6. Update `accounts.balance_minor` by `+amount` for credit or `-amount` for debit.
7. Commit and return the inserted row plus post-transaction balance.

The row lock serializes writes to the same account, avoiding lost updates. The unique constraint is the final guard against races or programming errors. Catch unique-constraint violations carefully and resolve the stored transaction as an idempotent duplicate where appropriate.

## Atomicity and consistency

The transaction row and account projection must commit or roll back together. Do not create the ledger entry and update balance in separate calls. Use database constraints for invariants that can be expressed there. For a failed debit, no transaction row is inserted and balance is unchanged.

As a useful invariant check, for an account without transfers the balance projection equals sum(credits) minus sum(debits). With transfers represented as debit+credit rows, this remains true. A small admin/debug reconciliation query can compare the projection to ledger sum, but it is not required as a public endpoint.

## Duplicate semantics

Idempotency key is `(account_id, reference_id)`. The first successful transaction is authoritative. A retry returns that row and never applies its amount again. Same reference on another account is allowed. A duplicate reference with a changed body must not mutate or replace the original transaction; return the original row with `duplicate: true` and optionally log a safe mismatch metric.

## History query

Filter by account and optional type; compute total count under the same filter; return limit/offset page with a stable order `created_at DESC, id DESC`. Clamp by rejecting `limit > 100`; reject page < 1 and non-integers. For large future datasets, move to cursor pagination; offset is sufficient for the assignment.

## Transfer bonus concurrency

- Validate source and destination IDs are distinct.
- Begin transaction and lock both account rows in ascending UUID order, regardless of transfer direction, preventing deadlocks between opposite-direction transfers.
- Verify both accounts exist and source has sufficient funds.
- Insert a linked debit and credit row; update both projections; commit once.
- Use a unique transfer reference/idempotency key. If either row insert or either balance update fails, rollback everything.

## Operational basics

- Structured logs include request ID, route, duration, and error code; never log secrets or full sensitive payloads.
- `/health` is liveness; a separate readiness check may ping the DB.
- Gracefully close HTTP server and DB client on SIGTERM.
- Migrations are committed and run explicitly at startup/deploy.
- Use bounded request body size and sane connection-pool defaults.
- No auth or tenant isolation is defined in the assignment. Make this limitation visible in the README.
